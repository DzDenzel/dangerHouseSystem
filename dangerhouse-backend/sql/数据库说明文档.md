# 危房智诊系统 - 数据库说明文档

> 版本：V3.0
> 脚本生成时间：2026-04-12
> 数据库：MySQL 8.0+
> 基准脚本：`dangerhouse_v3.0.sql`（结构 + 初始化数据）、`dangerhouse_v3.0_with_data.sql`（结构 + 业务示例数据）

---

## 1. 数据库概览

- 数据库名：`dangerhouse`（对应 `spring.datasource.url`）
- 字符集：utf8mb4（脚本首行 `SET NAMES utf8mb4`）
- 表数量：8，两个脚本的表结构与索引完全一致，差异只在初始化数据（见第 6 节）
- 存储引擎与排序规则脚本里没有显式声明，走 MySQL 8.0 默认值（InnoDB / utf8mb4_0900_ai_ci）

### 表清单

| 表名 | 中文名 | 说明 |
|------|--------|------|
| building | 建筑档案表 | 建筑基本信息、归属与跟进人 |
| role | 角色表 | 角色定义 |
| user | 用户表 | 系统用户账号 |
| user_role | 用户角色关联表 | 用户与角色的多对多关系 |
| detection | AI检测记录表 | 检测任务与聚合结果 |

| report | 检测报告表 | 报告文件记录 |

## 3. 枚举与数据字典

### 3.1 状态位（user.status / operation_log.status）

两个字段取值相同：

| 值 | user.status | operation_log.status |
|----|-------------|----------------------|
| 1 | 正常（默认） | 成功（默认） |
| 0 | 禁用 | 失败 |

### 3.2 role.role_code

| 编码 | 角色名称 | 说明 |
|------|----------|------|
| ADMIN | 管理员 | 系统最高权限 |
| INSPECTOR | 检测员 | 移动端执行建筑采集与检测 |
| USER | 普通用户 | 移动端快速检测、查看个人建筑与个人信息 |

### 3.3 building.structure_type

取值来自 SQL 列注释，共 5 个：`BRICK_MIX`、`CONCRETE`、`STEEL`、`BRICK_WOOD`、`OTHER`。库里存代码，不存中文。

### 3.4 detection.status

状态流转：`CREATED` →（上传图片）`READY` →（启动检测）`PROCESSING` → `COMPLETED` / `FAILED`；只有 `CREATED`、`READY` 允许取消为 `CANCELLED`。

| 状态 | 说明 |
|------|------|
| CREATED | 已创建，空任务（默认值） |
| READY | 已上传图片，待分析 |
| PROCESSING | 分析中 |
| COMPLETED | 已完成 |
| FAILED | 失败，原因写 `error_message` |
| CANCELLED | 已取消 |

### 3.5 detection.risk_level

代码里 `RiskLevel` 枚举定义了等级、损伤比例分档与展示色：

| 等级 | 别名（旧代码） | 损伤比例 | 说明 | 颜色 |
|------|----------------|----------|------|------|
| A | LOW | < 5% | 低风险 | #28A745 |
| B | MEDIUM | 5% - 15% | 中风险 | #FFC107 |
| C | HIGH | 15% - 30% | 高风险 | #FD7E14 |
| D | CRITICAL | ≥ 30% | 严重风险 | #DC3545 |

多步流程（创建任务 → 上传图片 → 启动检测）里，`createTask` 不写这个字段，`startDetection` 还会显式置空，最终值来自检测完成后 AI 返回的 `severityLevel`；一步式的 `uploadAndDetectMultiple` 会先写一个占位的 `A`，再被 AI 结果覆盖。所以库里的 `risk_level` 不一定严格等于按 `damage_ratio` 分档算出来的等级，示例数据里 `detection.id=5` 的 `damage_ratio=10.90`、`risk_level=C` 就是这种情况。

### 3.6 image.image_type

这个字段三种口径对不上，按事实分别列出：

| 来源 | 取值 |
|------|------|
| SQL 列注释 | 墙体 / 屋顶 / 整体 |
| 实体类 `Image.java` 注释 | ORIGINAL-原图 / RESULT-结果图 |
| 代码实际写入 | 只有 ORIGINAL |
| 示例数据 | 只有 ORIGINAL（12 条 image 记录全部如此） |

`DetectionServiceImpl` 在单张上传与批量上传两处都硬编码 `image.setImageType("ORIGINAL")`，`uploadAndDetectMultiple(buildingId, files, imageType)` 虽然收了 `imageType` 入参但方法体内没有使用。AI 结果图不另开一行记录，而是回写到同一行 image 的 `result_image_path`。因此 `image_type` 当前等价于「原图」标记，`idx_image_type` 这个索引选择性极低。

### 3.7 report.file_type

SQL 注释与实体类注释给的值是 `PDF` / `WORD`，默认 `PDF`。`GenerateReportRequest` 的注释写的是 `PDF/DOCX`，`DetectionReportServiceImpl` 会把入参转成大写、缺省补 `PDF`，但报告生成与下载链路实际只做 PDF（下载响应 `Content-Type` 为 `application/pdf`）。

## 4. 索引

### 4.1 唯一约束

| 表 | 约束名 | 字段 |
|----|--------|------|
| user | uk_username | username |
| user | uk_email | email |
| role | uk_role_code | role_code |
| user_role | uk_user_role | (user_id, role_id) |
| report | uk_report_no | report_no |

### 4.2 普通索引

8 张表都用 `id BIGINT AUTO_INCREMENT` 作主键，下面只列建表语句里显式创建的索引，索引名都是 `idx_字段名`：

| 表 | 索引字段 |
|----|----------|
| user | created_at、status |
| building | address、created_at、name、owner_user_id |
| detection | building_id、detect_time、risk_level、status、user_id |
| image | detection_id、image_type |
| report | building_id、detection_id、generated_at |
| operation_log | create_time、operation、status、user_id |
| user_role | role_id、user_id |

## 5. 外键约束

| 从表 | 外键名 | 从表字段 | 主表 | 主表字段 | 删除规则 |
|------|--------|----------|------|----------|----------|
| detection | fk_detection_building_id | building_id | building | id | CASCADE |
| detection | fk_detection_user_id | user_id | user | id | SET NULL |
| image | fk_image_detection_id | detection_id | detection | id | CASCADE |
| report | fk_report_building_id | building_id | building | id | CASCADE |
| report | fk_report_detection_id | detection_id | detection | id | CASCADE |
| operation_log | fk_log_user_id | user_id | user | id | SET NULL |
| user_role | fk_ur_role_id | role_id | role | id | CASCADE |
| user_role | fk_ur_user_id | user_id | user | id | CASCADE |

CASCADE 表示删主表记录时连带删掉从表记录，SET NULL 表示把从表字段置空。实际影响：删建筑会连带删掉该建筑下的 detection、image、report；删检测记录会连带删掉它的 image 和 report；删用户只把 detection、operation_log 的用户字段置空，但用户角色关联记录会被删掉。

## 附录

### A. 执行脚本

```bash
# 只有结构 + 角色/管理员账号
mysql -u root -p < dangerhouse_v3.0.sql

# 结构 + 角色/用户/建筑/检测/图片/报告示例数据
mysql -u root -p < dangerhouse_v3.0_with_data.sql
```

两个脚本开头都关掉了外键检查（`SET FOREIGN_KEY_CHECKS = 0`），按依赖倒序 DROP 表后重建，可以直接在已有库上重跑。重跑会清空数据。

### B. 数据源配置

对应 `dangerhouse-backend/src/main/resources/application.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/dangerhouse?serverTimezone=Asia/Shanghai&useSSL=false&characterEncoding=utf8
    username: root
    password: <按本地环境填写>
    driver-class-name: com.mysql.cj.jdbc.Driver
```
